## Context

当前群相册功能基于messages表实现，没有独立的相册数据模型。前端GroupAlbum组件已实现基本框架，但上传和创建相册功能只是TODO占位。大图预览组件不支持左右切换，分页逻辑存在bug。

**现有架构：**
- 图片存储：聊天图片通过StoreUpload()保存到磁盘，URL存储在Messages表
- 数据查询：GetGroupImages()从Messages表筛选message_type="image"的消息
- 前端组件：GroupAlbum.tsx实现网格展示，ImagePreviewModal.tsx实现单张预览

**约束条件：**
- 使用SQLite数据库，GORM作为ORM
- 文件上传使用现有的multipart处理机制
- 前端使用React + TypeScript

## Goals / Non-Goals

**Goals:**
- 实现完整的相册管理系统，支持创建、编辑、删除相册
- 支持直接上传图片到相册，不经过聊天消息
- 实现群动态和与我相关功能
- 改进大图预览体验
- 修复分页bug

**Non-Goals:**
- 不实现图片编辑功能（裁剪、滤镜等）
- 不实现相册分享功能
- 不实现图片评论功能
- 不实现相册排序功能（按创建时间固定排序）

## Decisions

### 1. 数据库设计决策

**决策：** 新增Album和AlbumPhoto表，独立于Messages表

**理由：**
- 相册需要独立的元数据（名称、描述、封面）
- 图片需要关联到特定相册，而不是平铺展示
- 需要支持相册级别的操作（删除相册会删除所有图片）

**替代方案：**
- 方案A：在Messages表增加album_id字段 → 缺点：破坏消息表结构，查询复杂
- 方案B：使用JSON字段存储相册信息 → 缺点：查询性能差，无法建立索引

**选择：** 方案C（独立表），因为结构清晰，查询高效，扩展性好

### 2. 图片存储决策

**决策：** 复用现有的文件上传机制，AlbumPhoto表存储文件URL

**理由：**
- 现有上传机制已经稳定可靠
- 文件URL格式统一，便于管理
- 可以复用现有的文件访问逻辑

**替代方案：**
- 方案A：新建独立的相册图片存储目录 → 缺点：需要额外的文件管理逻辑
- 方案B：将图片转换为Base64存储 → 缺点：数据库体积膨胀，查询性能差

**选择：** 方案C（复用现有机制），因为简单可靠，维护成本低

### 3. API设计决策

**决策：** 新增10个RESTful API接口，遵循现有API风格

**理由：**
- 相册管理需要完整的CRUD操作
- 图片上传需要独立的接口
- 群动态和与我相关需要独立的查询接口

**替代方案：**
- 方案A：扩展现有group_files接口 → 缺点：接口职责不清，参数复杂
- 方案B：使用GraphQL → 缺点：学习成本高，与现有架构不匹配

**选择：** 方案C（独立RESTful接口），因为清晰明确，易于理解和维护

### 4. 前端组件设计决策

**决策：** 重构GroupAlbum组件，新增AlbumList、AlbumDetail、AlbumUploader子组件

**理由：**
- 职责分离，每个组件专注单一功能
- 便于维护和测试
- 支持复杂的交互逻辑

**替代方案：**
- 方案A：在现有GroupAlbum中实现所有功能 → 缺点：组件过于臃肿，难以维护
- 方案B：使用状态管理库 → 缺点：增加复杂度，当前规模不需要

**选择：** 方案C（组件拆分），因为符合React最佳实践，易于扩展

### 5. 分页策略决策

**决策：** 使用分页按钮，每页20条数据

**理由：**
- 用户明确要求分页按钮
- 20条数据适合网格展示，不会过多
- 分页按钮直观易用

**替代方案：**
- 方案A：无限滚动 → 缺点：用户明确拒绝
- 方案B：加载更多按钮 → 缺点：用户明确选择分页按钮

**选择：** 方案C（分页按钮），因为符合用户需求

## Risks / Trade-offs

### 风险1：数据库迁移
- **风险：** 新增表可能影响现有数据
- **缓解：** 使用GORM AutoMigrate，自动处理表结构变更，支持回滚

### 风险2：文件存储一致性
- **风险：** 相册图片和聊天图片可能产生重复存储
- **缓解：** 复用现有上传机制，避免重复存储；可以后续优化去重逻辑

### 风险3：性能影响
- **风险：** 大量图片查询可能影响性能
- **缓解：** 使用分页限制返回数量；建立适当的数据库索引；可以后续添加缓存

### 风险4：用户体验
- **风险：** 新功能可能让用户困惑
- **缓解：** 保持现有UI风格，提供清晰的引导和提示

## Migration Plan

### 部署步骤
1. 后端部署：新增模型和API接口
2. 数据库迁移：AutoMigrate自动创建新表
3. 前端部署：更新组件和API调用
4. 功能验证：测试所有新功能

### 回滚策略
- 数据库：AutoMigrate支持回滚，可以删除新增的表
- 后端：保留旧版本代码，可以快速回滚
- 前端：保留旧版本组件，可以快速回滚

   - 决定：需要实现权限控制，创建者和管理员可编辑/删除

   - 决定：需要显示上传进度，提升用户体验
