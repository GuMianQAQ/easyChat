## Context

当前截图功能流程：用户点击截图按钮 → Electron 截全屏 → 用户选择区域 → 返回聊天界面预览 → 发送。

选择器窗口使用 `data:text/html` 加载纯 HTML/JS，无法使用 npm 包和 React 生态。用户需要在截图后进行标注（画笔、文字、形状、马赛克），纯 JS 实现这些功能代码量大且难维护。

项目已有多窗口模式：主窗口和 moments 窗口共享同一 React 应用，通过 URL 参数 `?window=moments` 区分。编辑器窗口可复用此架构。

## Goals / Non-Goals

**Goals:**
- 截图选择区域后自动打开编辑器窗口
- 支持画笔、文字、箭头、矩形、圆形、马赛克编辑工具
- 支持撤销/重做
- 编辑完成后导出图片返回聊天界面预览
- 保留原有 1MB 图片大小限制
- 编辑器窗口使用 React + TypeScript，复用项目架构

**Non-Goals:**
- 不支持裁剪（用户明确排除）
- 不支持多显示器截图
- 不支持图片旋转/翻转
- 不支持图层管理
- 不支持从文件打开图片编辑（仅限截图）

## Decisions

### 1. 编辑器窗口使用独立 BrowserWindow + React 路由

**选择**: 创建独立 BrowserWindow，通过 `${DEV_SERVER_URL}?window=editor` 加载，App.tsx 中根据 URL 参数渲染编辑器组件。

**理由**:
- 复用项目已有的多窗口模式（moments 窗口已验证可行）
- 可使用 React + TypeScript + npm 包
- 编辑器组件可复用项目中的样式和工具函数

**替代方案**:
- data: URL 加载纯 HTML：无法使用 npm 包，代码难维护
- 在选择器窗口内扩展：选择器代码会变得臃肿，职责不清晰

### 2. 使用 fabric.js 作为 Canvas 编辑框架

**选择**: fabric.js

**理由**:
- 对象模型清晰，每个形状是独立对象，便于撤销/重做
- 原生支持画笔、文字、形状绘制
- 事件系统完善，交互实现简单
- 文档和社区成熟

**替代方案**:
- konva.js + react-konva：React 声明式 API，但对象模型不如 fabric.js 灵活
- tui-image-editor：功能齐全但过于重量级，很多功能用不到
- 原生 Canvas API：需要手写所有交互逻辑，工作量大

### 3. 截图数据通过 IPC 传递

**选择**: 选择器确认后，主进程将截图 dataURL 通过 IPC 发送给编辑器窗口。

**数据流**:
```
选择器确认选区
    │
    ▼
主进程裁剪图片
    │
    ▼
主进程创建编辑器窗口
    │
    ▼
IPC 发送 dataURL 给编辑器
    │
    ▼
编辑器加载图片到 fabric.js Canvas
```

**理由**: 主进程已有裁剪逻辑，直接复用。编辑器窗口创建时接收数据，无需额外存储。

### 4. 编辑器窗口大小自适应截图区域

**选择**: 编辑器窗口大小根据截图区域比例适配，最大不超过屏幕 80%。

**理由**: 截图区域可能是任意比例，固定大小会导致图片变形或留白过多。

## Risks / Trade-offs

- **[fabric.js 包体积]** → fabric.js 约 300KB，对启动速度有轻微影响。可接受，编辑器窗口是按需创建的。
- **[编辑器窗口与主窗口通信]** → 需要确保 IPC 通信可靠，编辑器关闭时正确清理资源。通过标准的窗口关闭事件处理。
- **[马赛克性能]** → 大区域马赛克需要处理大量像素，可能导致卡顿。通过限制马赛克笔刷大小和使用 requestAnimationFrame 优化。
- **[撤销/重做内存]** → 操作历史会占用内存。限制历史栈大小（如 50 步），超出时丢弃最早的操作。
